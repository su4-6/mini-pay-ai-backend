## 1. 产品背景

### 1.1 背景与机会

MiniPay 已具备 Android 登录、用户身份、支付授权、站内转账、钱包余额、账单、支付和退款等基础能力，但用户仍需要进入多个固定页面完成操作。当前 `agent-service` 仅提供聊天会话与消息存储骨架，尚未接入 LLM、SSE 流式对话、白名单工具、长期记忆或业务编排；Android AI 首页中的自然语言提交和生活助手也仍是占位入口。

本模块将 AI 对话升级为 Android 端统一的智能支付与生活服务入口。用户可用自然语言表达目标，由 AI 识别意图、补齐必要信息、调用受控工具并展示结构化确认卡；涉及资金、订单取消或退款的动作仍由用户在可信原生界面显式确认。

### 1.2 对标原则

本产品不复制对标产品的品牌、界面或不可见内部实现，只采用以下公开可验证的交互原则：

1. **支付宝式交易安全：** 用户授权、支付意图校验、明确确认、交易留痕、结果可追溯。
2. **千问式任务完成：** 用户自然表达需求，AI 结合上下文补槽和推荐，用户选择方案并完成确认付款。
3. **MiniPay 既有资金边界：** AI 不能接收支付密码，不能签发支付授权，不能直接扣款或修改余额。

### 1.3 当前实现基线

| 能力 | 当前状态 | 本 PRD 目标 |
|---|---|---|
| Android AI 首页 | 已有页面、快捷入口和输入框，业务动作多为占位 | 接入真实 AI 会话、结构化卡片和原生确认流程 |
| Agent 会话 | 仅有聊天 CRUD；契约与实现不完整 | 会话管理、SSE、工具编排、执行追踪和记忆 |
| 站内转账 | 已有意图、一次性支付授权、TCC 转账链路 | 增加自然语言补槽、联系人消歧和结果卡片 |
| 钱包与账单 | 已有余额、账单列表和详情 API | 增加自然语言查询与确定性聚合分析 |
| 外卖 | `commerce-service` 仅为占位；当前架构排除外卖 | 建设独立沙箱 Commerce 领域和完整演示闭环 |
| Android 外卖载体 | 预留受控 WebView，未接业务 | P0 改为 AI 对话原生卡片；真实外卖 H5 接入放 P1 |

## 2. 产品目标与范围

### 2.1 产品目标

用户在 Android App 的 AI 对话中，通过文字完成以下三类任务：

1. 给指定联系人发起站内转账，并在原生安全页确认付款。
2. 查询钱包余额、账单和收支分析，获得可核验的结构化结果。
3. 根据自然语言需求选择沙箱外卖、确认订单、使用钱包付款并跟踪履约或退款。

### 2.2 成功标准

| 指标 | MVP 目标 |
|---|---|
| 标准脚本任务完成率 | ≥ 95% |
| 权威金额与状态一致率 | 100% |
| 未经用户确认执行资金动作 | 0 次 |
| 越权工具调用 | 0 次 |
| SSE 首个可见响应 P95 | ≤ 2.5 秒 |
| 最后一个必填信息补齐后生成卡片 P95 | ≤ 5 秒 |
| 重试造成重复转账、订单或付款 | 0 次 |

性能指标在本地或指定沙箱验收环境、依赖服务健康的前提下计算；外部模型不可用时间单独统计。

### 2.3 目标用户

- 已完成 MiniPay Android 登录和首次开户的消费者。
- 发起资金操作时，用户还需满足既有实名、支付密码、设备和账户状态要求。
- P0 只支持中文文字输入，不针对未登录访客、商户端或运营端提供 AI 助手。

### 2.4 P0 范围

- AI 会话、消息历史、流式输出和结构化卡片。
- AI 站内转账。
- 钱包余额、账单查询和收支聚合分析。
- 沙箱商家、菜单、购物车、地址、优惠、外卖订单和模拟配送。
- 钱包余额支付、订单取消和全额退款。
- 用户显式授权的长期记忆。
- 模型不可用、工具失败、网络中断和 SSE 重连降级。

### 2.5 非 P0 范围

- 真实资金、真实商家、真实骑手或真实外卖履约。
- 语音输入、图片点餐和拍照识别菜单。
- 支付宝、微信或银行卡支付外卖订单。
- 自动付款、小额免确认、定时转账或周期性付款。
- 全平台昵称、实名或手机号片段模糊找人。
- 充值、提现代办；AI 仅可解释并跳转现有传统页面。
- 部分退款、缺货协商、申诉仲裁、发票和复杂售后。
- 主动营销、广告排序或基于敏感财务信息的推荐。

## 3. 产品原则

### 3.1 人在回路

- 查询类工具可在用户发问后直接执行。
- 创建转账意图、结算意图等“准备动作”不得产生资金变化，可由 AI 在信息完整后执行。
- 转账付款、外卖付款、取消已付款订单和发起退款必须展示确认卡并由用户主动点击。
- 支付确认必须进入 Android 原生页，通过 Identity 校验支付密码并签发一次性授权；AI 无权代替该步骤。

### 3.2 权威数据优先

- AI 文本不是业务事实来源。
- 收款人身份由 Identity/联系人目录返回；余额和账单由 Wallet 返回；转账状态由 Payment 返回；商品、库存、报价和外卖状态由 Commerce 返回。
- 金额、库存、优惠、配送费、订单状态和交易状态必须使用确定性组件直接渲染工具结果，禁止由模型自行填写。

### 3.3 最小数据暴露

- 完整手机号只在本地预处理和 Identity 精确解析接口中短暂使用，不进入模型请求、持久化会话、记忆、日志或 Trace。
- 完整配送地址只交给 Commerce；模型仅获得地址标签、地址 ID 和脱敏摘要。
- 余额、账单明细不发送给模型。需要分析时，由 Wallet/Agent 确定性聚合后仅向模型提供限定时间范围的脱敏汇总，或直接使用模板解释。
- 登录密码、支付密码、验证码、Cookie、Authorization 头、完整 Token、一次性支付授权令牌和私钥在任何情况下都不得进入 AI 上下文。

### 3.4 单一活动写任务

一个会话同一时间只允许存在一个活动的转账或点餐写任务。用户切换任务时：

1. 无业务意图已创建时，旧草稿自动结束。
2. 已生成待确认意图时，先提示用户“继续当前任务”或“取消并开始新任务”。
3. 已进入支付或处理中状态时，不得创建重复任务，只能查询当前状态或等待恢复。

## 4. 信息架构与核心交互

### 4.1 AI 首页

AI 首页保持现有“米灵”品牌和对话主入口，包含：

- 会话侧边栏：新建、搜索、选择、重命名和删除会话。
- 文字输入框：最多 1,000 个 Unicode 字符；禁止提交纯空白内容。
- 快捷入口：转账、查余额、看账单、点外卖。
- 推荐问题：如“帮我给小李转 50 元”“这个月餐饮花了多少”“想点一杯 20 元以内的无糖奶茶”。
- 消息流：文本、工具进度、候选项、交易卡、商品卡、购物车卡、订单卡和安全提示。
- 停止按钮：仅停止模型生成，不取消已创建的业务意图或进行中的交易。

### 4.2 会话管理

| 功能 | 产品规则 |
|---|---|
| 新建会话 | 创建空会话并切换；当前存在未确认写任务时先提示处理 |
| 会话标题 | 首条有效用户消息后自动生成；用户可手动修改，最长 40 字 |
| 搜索 | 仅搜索当前用户自己的标题和已持久化消息摘要 |
| 删除 | 二次确认；删除消息与普通工具展示记录，不删除支付、钱包、外卖业务事实和审计记录 |
| 历史加载 | 按游标分页，默认每页 30 条；进入会话后定位到最新消息 |
| 并发设备 | 服务端版本或游标为准；不允许两个设备重复确认同一业务意图 |

### 4.3 通用多轮补槽

AI 只追问完成当前任务所需的信息，且一次优先询问一个高价值缺失项。用户可在后续消息中修改尚未确认的字段；已经生成权威意图或报价后，修改金额、收款人、商品、数量、地址或优惠必须重新准备新的意图，旧意图标记为已替换或取消。

## 5. AI 转账

### 5.1 用户故事

> 作为已登录用户，我希望说“给小李转 50 元”，由 AI 帮我找到正确的联系人、补齐转账信息并生成确认卡，但只有我完成安全确认后资金才会转出。

### 5.2 支持的表达

- “给小李转 50 元。”
- “转 20 给 13800138000，备注午饭。”
- “刚才那笔转账怎么样了？”
- “不要转了。”

P0 不支持从图片、剪贴板联系人卡、群聊 `@` 或银行卡号解析收款人。

### 5.3 收款人解析

1. **完整手机号：** 客户端或 Agent 安全预处理器识别完整中国大陆手机号，使用 Identity 精确解析；发送给模型的文本以占位标识替换手机号。
2. **联系人昵称：** 只在当前用户已建立的联系人关系中查询。
3. **唯一匹配：** 展示昵称、头像和脱敏手机号/实名，等待其他槽位补齐。
4. **多个匹配：** 展示最多 5 个候选项，用户必须点击选择；模型不得自行猜测。
5. **无匹配：** 返回统一的不可枚举提示，建议用户检查完整手机号或前往联系人页。
6. **自己、无效或受限账户：** 阻止创建意图并展示安全文案。

### 5.4 必填信息

| 字段 | 规则 |
|---|---|
| 收款人 | 必填；必须解析为唯一有效的用户 ID |
| 金额 | 必填；人民币分的正整数；沿用 Payment 既有限额与年度限额规则 |
| 备注 | 选填；最长 50 字；内容安全校验 |
| 来源 | 固定为 `AI` |

### 5.5 主流程

1. 用户表达转账意图。
2. AI 解析槽位并调用联系人查询；缺失或歧义时继续追问。
3. 信息完整后，Agent 调用 Payment 的受控准备工具创建不可变转账意图。
4. 对话展示转账确认卡，不执行扣款。
5. 用户点击“确认转账”，Android 进入原生付款确认页。
6. 用户输入支付密码；Identity 签发绑定用户、设备、意图、金额和时效的一次性授权。
7. Android 将一次性授权提交给 Payment 确认转账。
8. Payment 与 Wallet 完成 TCC；结果为成功、失败或处理中。
9. Android/Agent 查询权威状态并更新原卡片；处理中只允许刷新，不允许重复创建。

### 5.6 转账确认卡

必须展示：

- 收款人头像、昵称、脱敏手机号和可选脱敏实名。
- 金额，使用“¥0.00”格式。
- 备注。
- 意图有效期。
- “确认转账”和“取消”按钮。
- “付款将进入原生安全确认页，AI 不会获取支付密码”说明。

按钮状态：待确认可操作；已过期只允许重新准备；处理中只允许查看进度；成功和失败不可重复确认。

### 5.7 异常处理

| 场景 | 产品行为 |
|---|---|
| 收款人重名 | 展示候选项，不自动选择 |
| 联系人不存在 | 不暴露账户是否存在，提示检查信息 |
| 金额缺失或不合法 | 追问或提示有效范围，不创建意图 |
| 意图过期 | 原卡失效；用户确认后按当前信息重新准备 |
| 余额不足 | 展示余额不足，可跳转充值页；AI 不代办充值 |
| 授权错误、过期或重放 | 停止确认并要求重新进入原生授权页 |
| TCC 处理中 | 展示处理中并轮询/订阅结果，不重复发起 |
| 最终失败 | 展示稳定失败码对应文案和可行动建议 |

## 6. 钱包查询与账单分析

### 6.1 用户故事

> 作为用户，我希望通过自然语言查询余额、近期交易和一段时间内的收支情况，且所有数字都能追溯到钱包账单。

### 6.2 P0 能力

- 当前钱包可用余额、冻结金额和沙箱提示。
- 最近 N 笔账单，N 默认 10，最大 50。
- 按自然语言解析时间范围、收支方向和业务类型。
- 单笔账单详情和关联业务单状态。
- 日、周、月范围内的收入、支出、净额和分类汇总。
- 解释“处理中、失败、退款中”等状态，但不承诺具体恢复时间。

### 6.3 查询示例

- “余额还有多少？”
- “最近 5 笔支出。”
- “这个月餐饮花了多少？”
- “上周转账收入和支出分别多少？”
- “刚才那笔 50 元为什么还在处理中？”

### 6.4 数据与展示规则

1. 余额卡、账单卡和汇总卡由应用根据 Wallet/Payment 的结构化响应确定性渲染。
2. 模型不得读取或复述未由工具返回的数字。
3. “今天、本周、本月”等范围按用户时区 Asia/Shanghai 解析，再转换为 UTC 查询边界。
4. 查询范围默认不超过 366 天；超出时提示缩小范围。
5. 账单列表必须分页，不得一次加载全部账单。
6. 账单分析只基于已入账或契约明确纳入统计的状态；处理中项目单独列示，不混入已完成汇总。
7. 若业务分类数据不足，显示“其他”，不得由模型猜测商户类别。

### 6.5 隐私策略

- 原始账单明细和余额不发送到外部模型。
- 复杂自然语言解释优先使用本地规则和模板。
- 确需模型润色时，仅提供时间范围、分类标签和聚合后的数值，不提供业务单号、联系人、手机号、地址或卡信息。

## 7. 沙箱外卖点餐

### 7.1 用户故事

> 作为用户，我希望说出预算、品类、口味和送达要求，由 AI 推荐可配送的沙箱商品，在对话中完成选品、购物车、订单确认、钱包付款和配送跟踪。

### 7.2 沙箱声明

所有商家、商品、优惠、地址、库存、骑手和配送状态均为模拟数据。外卖相关页面与卡片必须持续展示“沙箱演示，不产生真实订单或配送”的明确标识。

### 7.3 商家与菜单

Commerce 独占以下权威数据：

- 沙箱商家、营业状态、配送区域、起送价、配送费和预计送达时间。
- 菜品、分类、规格、加料、价格、库存、口味标签和商家提供的过敏原标签。
- 购物车、地址、优惠、结算报价、外卖订单和配送状态。

AI 只能根据工具返回的商家和商品进行推荐，不得虚构菜品、价格、折扣、库存、销量、评分或配送时间。

### 7.4 需求理解与推荐

支持识别：

- 品类或具体商品，如奶茶、盖饭、咖啡。
- 预算，包括商品预算或订单总预算。
- 口味与规格，如少糖、无糖、不要辣、大杯。
- 忌口和用户明确声明的过敏原。
- 人数、数量和期望送达时间。
- 商家或配送偏好。

当信息不足时，AI 可直接返回通用候选，不强制追问所有偏好；只有地址、商品规格、数量等下单必需信息缺失时才必须追问。

推荐顺序由 Commerce 返回的可配送性、匹配度、预计送达、实付价等确定性特征生成。模型只负责以自然语言解释已返回的匹配原因。广告或商业加权不进入 P0。

### 7.5 忌口与过敏原

- 记忆中的忌口用于筛选或降权，但每次订单确认仍展示相关提示。
- 过敏原标签以商家沙箱数据为准，AI 不作医疗保证。
- 商品缺少过敏原信息时，显示“信息未提供”，不得推断为安全。
- 用户表达严重过敏时，必须提示核对商家信息，不能仅凭 AI 推荐下单。

### 7.6 原生结构化卡片

#### 商家卡

展示商家名称、沙箱标识、营业状态、配送费、起送价、预计送达时间和匹配标签。

#### 商品卡

展示商品图片、名称、基础价、可选规格、库存状态、口味/过敏原标签和“加入购物车”按钮。

#### 购物车卡

展示商家、商品、规格、单价、数量、商品小计、配送费、优惠、预计实付和地址脱敏摘要；允许增减数量、删除商品和进入结算。

同一购物车只能包含一个商家的商品。用户选择另一商家商品时，必须提示清空或保留原购物车，不得静默清空。

### 7.7 地址

- Commerce 管理沙箱配送地址，P0 支持新增、编辑、删除和选择。
- 模型仅接收地址 ID、标签和如“公司（朝阳区***路）”的脱敏摘要。
- 完整联系人、手机号、门牌号仅在 Commerce 和原生地址页使用。
- 长期记忆只保存用户明确同意的“常用地址 ID”，不保存地址正文。
- 地址超出商家模拟配送范围时，不能创建结算意图。

### 7.8 优惠与报价

- P0 支持单张沙箱优惠券或商家优惠，默认由 Commerce 选择当前最优的可用优惠。
- 商品金额、包装费、配送费、优惠和实付金额均由 Commerce 计算。
- 结算意图必须包含版本、有效期和权威金额；AI 与 Android 不得提交或修改权威金额。
- 库存、价格、地址或优惠变化时，旧报价立即失效，需重新结算并再次由用户确认。

### 7.9 点餐与付款主流程

1. 用户描述点餐需求。
2. AI 查询可配送商家和菜单，展示候选卡。
3. 用户选择商品、规格和数量；AI 调用受控购物车工具。
4. 用户选择沙箱地址；Commerce 校验配送范围、库存和营业状态。
5. Agent 请求 Commerce 生成有时效的权威结算意图。
6. 对话展示订单确认卡，包含所有费用、优惠、地址摘要和预计送达时间。
7. 用户点击“确认下单并付款”。
8. Android/Commerce 创建 `PENDING_PAYMENT` 外卖订单，并通过幂等内部契约请求 Payment 创建钱包支付单。
9. Android 进入原生付款页；Identity 签发一次性支付授权，Payment 调用 Wallet 完成钱包付款。
10. Payment 通过可靠事件通知 Commerce；Commerce 将订单推进为已支付并启动模拟履约。
11. 对话订单卡根据 Commerce 权威状态更新。

### 7.10 订单确认卡

必须展示：

- 商家名称和沙箱标识。
- 商品、规格、单价、数量和小计。
- 包装费、配送费、优惠和实付金额。
- 地址标签和脱敏摘要。
- 预计送达时间。
- 唯一可用支付方式“MiniPay 钱包余额”。
- 结算意图有效期。
- “确认下单并付款”和“返回修改”按钮。

### 7.11 外卖订单状态

| 状态 | 用户含义 | 允许动作 |
|---|---|---|
| `PENDING_PAYMENT` | 待付款 | 付款、取消 |
| `PAID` | 已付款，等待商家接单 | 查看、取消并申请全额退款 |
| `ACCEPTED` | 商家已接单 | 查看；P0 不支持用户主动取消 |
| `PREPARING` | 制作中 | 查看 |
| `DELIVERING` | 配送中 | 查看模拟配送进度 |
| `DELIVERED` | 已送达 | 查看订单 |
| `CANCELLED` | 已取消 | 查看取消原因 |
| `REFUND_PROCESSING` | 退款处理中 | 查看，不得重复申请 |
| `REFUNDED` | 已全额退款 | 查看退款结果 |
| `REFUND_FAILED` | 退款失败 | 查看安全失败说明和重试/人工排查入口 |

状态持久化使用稳定英文枚举；中文仅用于界面展示。

### 7.12 模拟履约

- 付款成功后，由 Commerce 的幂等任务按配置推进 `PAID → ACCEPTED → PREPARING → DELIVERING → DELIVERED`。
- 每次推进产生版本化事件和时间戳；应用重启后可恢复。
- 测试环境可配置各阶段延迟和失败注入，但普通用户不能任意修改状态。
- Agent 只查询或订阅状态，不直接推进订单。

### 7.13 取消与全额退款

1. 待付款订单可直接取消，不产生退款。
2. 已付款但未接单订单，用户可在对话订单卡点击取消；必须二次确认。
3. Commerce 先记录取消请求，再通过可靠事件/幂等 API 请求 Payment 创建全额退款。
4. Payment 与 Wallet 完成原路资金冲正，禁止直接修改余额或账本。
5. Commerce 消费退款结果并推进为 `REFUNDED` 或 `REFUND_FAILED`。
6. 退款处理中不得重复创建退款；同一订单 P0 只允许一次全额成功退款。
7. 退款属于资金回退，不要求再次输入支付密码，但必须有当前登录会话、明确点击和完整审计。

### 7.14 点餐异常处理

| 场景 | 产品行为 |
|---|---|
| 商家休息或不可配送 | 从候选中移除或禁用，并解释原因 |
| 商品售罄 | 禁止加入/结算，推荐同商家可用替代项 |
| 规格缺失 | 必须让用户选择，不使用模型猜测默认值 |
| 价格或优惠变化 | 旧确认卡失效，显示差异并重新确认 |
| 地址缺失/超区 | 引导选择或新增地址，不创建结算意图 |
| 钱包余额不足 | 订单保持待付款直至过期，可跳转充值页 |
| 支付处理中 | 展示处理中，不重复创建订单或支付单 |
| 支付失败 | 保留待付款或按规则关闭，展示可行动建议 |
| 退款处理中 | 只查询结果，不重复发起 |
| 模型不可用 | 保留商家搜索、购物车和订单传统确定性入口 |

## 8. 长期记忆

### 8.1 允许的记忆类型

| 类型 | 示例 | 保存条件 |
|---|---|---|
| 餐饮偏好 | 喜欢清淡、常点咖啡 | 用户明确点击“记住” |
| 忌口/过敏原偏好 | 不吃香菜、避免花生 | 用户明确点击“记住”；下单仍需核对 |
| 预算习惯 | 工作日午餐通常 30 元以内 | 用户明确点击“记住” |
| 联系人别名 | “房东”对应已选联系人 ID | 用户明确选择联系人并同意保存 |
| 常用地址引用 | “公司”对应 Commerce 地址 ID | 用户明确选择地址并同意保存 |

### 8.2 禁止保存

- 完整手机号、完整地址、身份证件、银行卡号或实名原文。
- 余额、账单明细、交易金额习惯或信用推断。
- 登录密码、支付密码、验证码、Token、Cookie、密钥或支付授权。
- 模型推断出的健康、宗教、政治等敏感属性。
- 未经用户确认从对话自动抽取的偏好。

### 8.3 用户控制

- 新记忆必须展示拟保存内容、用途和“记住/不记住”按钮。
- 用户可在“我的—长期记忆”中查看、修改和逐条删除。
- 支持“一键清空 AI 记忆”；不影响支付、订单、账本和法定审计记录。
- 引用的联系人或地址失效后，记忆自动标记不可用并提示用户重新选择。

## 9. Agent 工具与权限模型

### 9.1 工具分级

| 等级 | 定义 | P0 工具示例 | 是否需额外确认 |
|---|---|---|---|
| R0 | 只读查询 | 查询联系人、余额、账单、商家、菜单、订单状态 | 用户发问即视为本次查询授权 |
| W1 | 可逆草稿/准备 | 调整购物车、准备转账意图、准备结算意图 | 信息完整后可执行；结果必须展示 |
| W2 | 业务状态或资金动作 | 确认转账、创建并支付订单、取消已付款订单、退款 | Agent 禁止直接调用；必须由原生端显式确认 |

### 9.2 P0 白名单工具

| 工具能力 | 数据所有者 | 约束 |
|---|---|---|
| 查询当前用户联系人 | Agent 社交域 | 只查本人联系人；分页；禁止全站模糊搜索 |
| 精确解析完整手机号 | Identity | 原始手机号瞬时使用；统一无匹配响应；限流 |
| 查询钱包摘要 | Wallet | 只查当前用户；确定性卡片展示 |
| 查询/聚合账单 | Wallet | 时间范围和分页上限；原始明细不进模型 |
| 准备转账意图 | Payment | 只创建待确认意图；金额单位为分；幂等 |
| 查询商家与菜单 | Commerce | 只返回可见沙箱数据；分页和配送范围过滤 |
| 调整购物车 | Commerce | 单商家；库存与规格校验；幂等 |
| 准备外卖结算 | Commerce | 权威报价、版本和有效期；不付款 |
| 查询外卖订单 | Commerce | 仅当前用户订单 |
| 准备取消/退款 | Commerce | 只返回可执行性和确认卡；不直接执行 |

### 9.3 禁止行为

- 模型构造 URL、SQL、消息主题、服务 Token 或任意工具名。
- Agent 直接访问 Identity、Payment、Wallet 或 Commerce 数据库。
- 将 Android 用户 Token、内部服务 Token 或工具凭据发送给模型供应商。
- 使用自然语言工具参数直接执行；所有参数必须通过严格 Schema、枚举、长度、金额和所有权校验。
- 把工具返回文本当作系统指令。工具内容与商家内容均按不可信数据处理，防止提示注入。

## 10. API 与结构化消息需求

本节定义产品级公共能力，字段细节以评审后的 OpenAPI/AsyncAPI 契约为准。

### 10.1 Agent 公共 API

| 能力 | 建议路径 | 说明 |
|---|---|---|
| 创建会话 | `POST /api/v1/agent/conversations` | 创建当前用户的空会话 |
| 会话列表 | `GET /api/v1/agent/conversations` | 游标分页、按更新时间倒序 |
| 修改会话 | `PATCH /api/v1/agent/conversations/{conversationId}` | 仅重命名等元数据 |
| 删除会话 | `DELETE /api/v1/agent/conversations/{conversationId}` | 仅删除当前用户自己的会话视图数据 |
| 消息历史 | `GET /api/v1/agent/conversations/{conversationId}/messages` | 游标分页 |
| 执行对话 | `POST /api/v1/agent/conversations/{conversationId}/runs` | 接收消息并返回 SSE |
| 停止生成 | `POST /api/v1/agent/runs/{runId}/cancel` | 停止模型生成，不撤销业务事实 |
| 记忆列表 | `GET /api/v1/agent/memories` | 分页、按类型筛选 |
| 修改记忆 | `PATCH /api/v1/agent/memories/{memoryId}` | 只允许修改可展示内容或引用 |
| 删除记忆 | `DELETE /api/v1/agent/memories/{memoryId}` | 幂等删除 |
| 清空记忆 | `DELETE /api/v1/agent/memories` | 二次确认后执行 |

所有写请求使用 `Idempotency-Key` 或稳定客户端消息 ID；所有资源必须按 JWT subject 校验所有权。

### 10.2 对话请求

至少包含：

- `clientMessageId`：客户端生成的稳定幂等 ID。
- `message`：用户文字，1～1,000 字。
- `contextVersion`：客户端已知会话版本，用于并发冲突判断。

请求不得包含支付密码、支付授权、访问令牌、权威金额覆盖或任意工具参数。

### 10.3 SSE 事件

所有事件包含 `eventId`、`eventType`、`payloadVersion`、`conversationId`、`runId`、`occurredAt`、`requestId`。P0 事件类型：

| 事件 | 用途 |
|---|---|
| `message.delta` | 文本增量 |
| `message.completed` | 文本消息完成 |
| `tool.started` | 展示安全的工具进度，不暴露参数明文 |
| `tool.completed` | 工具成功摘要 |
| `choice.card` | 联系人、商家、商品、规格等候选选择 |
| `wallet.card` | 钱包摘要 |
| `bills.card` | 账单列表或聚合 |
| `transfer.confirmation.card` | 转账确认 |
| `merchant.card` | 商家候选 |
| `product.card` | 商品与规格 |
| `cart.card` | 购物车 |
| `food.checkout.card` | 外卖订单确认 |
| `payment.required` | 请求 Android 进入原生付款页，仅携带业务意图引用 |
| `task.result` | 任务最终状态 |
| `task.error` | 稳定错误码和安全文案 |
| `stream.completed` | 本次流结束 |

SSE 断线重连使用 `Last-Event-ID` 或等价游标；重放展示事件不得重新执行工具或创建业务单。

### 10.4 结构化卡片通则

- 每种卡片有独立 `cardType` 和 `cardVersion`。
- 卡片携带业务资源 ID、显示数据、允许动作和过期时间，不携带密码、Token 或完整敏感信息。
- Android 只执行枚举化动作，不解析模型文本决定导航或付款。
- 卡片过期或业务版本变化时，服务端拒绝动作并返回最新状态。

## 11. 服务边界与一致性

### 11.1 数据所有权

| 服务 | 独占数据/职责 |
|---|---|
| Agent | AI 会话、消息、运行、工具 Trace、显式记忆、联系人关系/别名 |
| Identity | 用户身份、精确手机号解析、支付密码校验、一次性支付授权 |
| Payment | 转账意图、转账单、支付单、退款单和支付编排 |
| Wallet | 余额、冻结、年度限额、账务事务、复式账本和账单 |
| Commerce | 沙箱商家、菜单、购物车、地址、报价、外卖订单和履约状态 |

服务间只能通过版本化 API、可靠事件或既有 TCC 分支协议协作，禁止跨服务查询或写数据库。

### 11.2 一致性模式

- 站内转账继续使用 Payment 编排和 Wallet Seata TCC。
- 外卖下单、支付和退款使用 Saga + 本地事务 + Outbox/Inbox + 幂等状态机，不使用长事务 TCC。
- Commerce 业务数据与 Outbox 在同一本地事务提交。
- Payment/Commerce 消费者使用 `eventId` 幂等；重复、乱序和延迟事件不得造成非法状态迁移。
- Wallet 继续独占余额和账本写入；退款通过正式冲正，不直接修余额。

### 11.3 外卖支付协作

1. Commerce 创建订单并保存权威报价。
2. Commerce 以业务唯一键向 Payment 请求钱包支付单；失败可安全重试。
3. Payment 校验来自 Commerce 的订单引用和金额，不采用 AI/客户端声明金额。
4. Payment 完成支付后发布版本化结果事件。
5. Commerce 幂等消费并推进外卖订单。
6. 超时或未知结果进入可恢复状态，由查询/重试任务收敛，不自动伪造成功或失败。

## 12. 安全、隐私与内容治理

### 12.1 鉴权

- Android 使用现有 Authorization Code + PKCE。
- Agent 公共 API 校验签名、issuer、audience、过期时间和 `agent.conversation` 等细分 scope。
- Agent 调用内部服务使用独立 Client Credentials 和最小工具 scope；用户 Token 与服务 Token 不互换。
- 所有会话、记忆、联系人、购物车和订单查询强制附加当前用户所有权条件。

### 12.2 提示注入与工具安全

- 系统指令、工具定义、用户输入和工具数据分层处理。
- 商家名称、商品描述、备注和工具错误文本均视为不可信内容，不能改变工具权限。
- 工具调用必须经过服务端策略引擎、Schema 校验、所有权校验和风险分级。
- 模型要求泄露提示词、凭据、内部地址或执行未登记操作时统一拒绝并记录安全指标。

### 12.3 日志与审计

允许记录：`requestId`、`traceId`、`runId`、脱敏业务 ID、工具名、执行耗时、结果码和模型版本。

禁止记录：完整用户输入中的敏感片段、完整手机号、完整地址、密码、验证码、Cookie、Authorization 头、完整 Token、支付授权、私钥和未经脱敏的工具参数。

每个 W1/W2 任务保留从用户消息、槽位确认、意图创建、用户点击、支付授权结果到最终业务状态的可追溯链路，但审计记录不保存敏感凭据。

### 12.4 数据保留默认值

- 普通 AI 会话与消息：沙箱默认保留 30 天，用户可提前删除。
- 显式长期记忆：保留至用户删除、引用失效或账号注销处理。
- Agent 工具审计：沙箱默认保留 180 天，仅保存最小元数据。
- Payment、Wallet、Commerce 的订单、退款和账务记录按各自业务与审计策略保留，不因删除 AI 会话而删除。

保留期限必须配置化，生产化前需重新完成隐私与合规评审。

## 13. 降级与容错

### 13.1 模型不可用

- 首页快捷入口继续可用。
- 余额、账单、联系人、商家搜索、购物车和订单状态提供确定性页面或表单入口。
- 已创建的转账、订单和支付状态仍可查询和恢复。
- 不用模板伪装为模型成功，不凭缓存猜测实时余额、库存或状态。

### 13.2 工具不可用

- 只读工具失败可由用户主动重试；服务端设置超时和熔断。
- 写工具超时先按幂等键查询结果，不直接重放。
- 无法确定结果时显示“结果确认中”，并保留 `requestId` 供排查。

### 13.3 客户端中断

- App 切后台、断网或进程重启后可恢复会话和活动任务。
- SSE 重连只补发已持久化展示事件。
- 原生付款页返回后必须按业务 ID 查询权威结果，不能只依赖页面回调。

## 14. 非功能需求

### 14.1 性能

- SSE 建连后尽快发送安全的 `tool.started` 或文本事件，避免长时间无反馈。
- 对话历史、联系人、账单、商家、菜单和订单列表全部分页并设置最大页大小。
- 工具调用设置独立超时；不在数据库行锁事务中调用模型或远程服务。

### 14.2 可观测性

至少提供以下指标：

- AI 请求量、首响应时间、总耗时、模型错误率和 Token 用量。
- 各工具调用量、成功率、延迟、超时率和拒绝率。
- 对话任务完成率、补槽轮次、用户取消率和确认卡转化率。
- 转账/点餐重复防护命中、授权失败、支付处理中和最终收敛时间。
- Outbox 积压、Inbox 重复、DLQ、未决支付/退款和订单状态异常。
- 敏感数据拦截和未授权工具调用尝试。

### 14.3 可访问性与体验

- 主要控件触控区域不小于 44dp。
- 卡片金额、状态和按钮具备无障碍语义。
- 不能只依靠颜色表达成功、失败或禁用。
- 流式内容更新避免抢夺屏幕阅读器焦点。

## 15. 埋点与产品分析

埋点只记录枚举、耗时和脱敏 ID，不记录用户原文、联系人、地址、备注或工具敏感参数。

| 事件 | 关键属性 |
|---|---|
| `agent_run_started` | intentCategory、entryPoint、modelProvider |
| `agent_slot_requested` | slotType、roundIndex |
| `agent_card_shown` | cardType、cardVersion |
| `agent_card_action` | cardType、actionType、resultCode |
| `agent_task_completed` | taskType、durationBucket、success |
| `agent_task_abandoned` | taskType、stage、reasonCode |
| `agent_tool_invoked` | toolName、riskLevel、latencyBucket、resultCode |
| `agent_fallback_used` | reasonCode、fallbackType |

金额不得作为通用埋点属性；财务分析指标从业务服务的受控统计获取。

## 16. 验收标准

### 16.1 AI 转账

- 输入“给小李转 50 元”时，唯一联系人可生成正确确认卡；重名时必须选择。
- 完整手机号可精确解析，但手机号不出现在模型请求、会话存储、日志或 Trace。
- 缺金额、非法金额、自己转自己、无效联系人均不能创建有效意图。
- 未点击确认或未通过原生支付授权时，钱包余额不得变化。
- 重复点击、网络重试、授权重放和 SSE 重连不会重复转账。
- 成功后付款方与收款方余额、账单、Payment 转账单一致；失败不伪造成功。

### 16.2 钱包与账单

- “余额多少”“最近 5 笔支出”“本月餐饮花费”返回与 Wallet 权威数据一致的卡片。
- 时间范围按 Asia/Shanghai 解释并正确转换为 UTC。
- 处理中项目不会计入已完成支出；退款和冲正口径有稳定规则。
- 模型无法虚构或覆盖余额、金额、账单状态。

### 16.3 外卖

- 用户可从自然语言需求完成推荐、规格选择、购物车、地址、结算、原生付款和模拟送达。
- 同一购物车只含一家商户，规格、库存、价格和优惠变化会触发重新确认。
- AI、Android 篡改金额不能改变 Commerce 权威报价或 Payment 金额。
- 未付款取消不产生退款；已付款未接单取消只创建一次全额退款。
- 支付、退款和履约事件重复、乱序或延迟时，订单最终收敛到合法状态。
- 余额不足、支付处理中、退款失败和服务不可用均有明确且可行动的文案。

### 16.4 安全与隐私

- 支付密码、验证码、完整 Token、手机号和地址不会进入模型、记忆、SSE、日志或埋点。
- 其他用户无法读取或操作当前用户的会话、联系人、记忆、购物车或订单。
- 提示注入不能扩大工具白名单或绕过 W2 用户确认。
- 删除会话/记忆不会删除或篡改支付、钱包、账本和外卖业务事实。

### 16.5 稳定性

- 模型不可用时，四个快捷入口仍提供可用的确定性降级路径。
- 工具超时、App 重启、SSE 重连不会重复创建业务单。
- 所有错误使用 RFC 9457 Problem Details 或版本化 SSE 错误事件，包含稳定 `code` 与 `requestId`。

## 17. 实施前置条件与依赖

本 PRD 定义目标产品，不表示以下能力已经实现。进入开发前必须完成：

1. 更新 `docs/architecture.md`，将 Commerce 从未来 P1 占位调整为沙箱 MVP 领域，并记录外卖与支付的 Saga/Outbox 协作。
2. 更新前端 `docs/PROJECT_STANDARDS.md` 和 Android 设计规范，批准 AI 原生外卖卡片取代当前 WebView-only 产品边界；受控 WebView 仍保留给 P1 真实外卖项目。
3. 更新 Agent、Identity、Payment、Wallet、Commerce 的 OpenAPI/AsyncAPI 契约和 OAuth scope。
4. 为新增表和索引创建新的 Flyway 迁移，不修改已发布迁移。
5. 建立可重复的沙箱商家、菜单、地址、优惠和履约测试数据。
6. 完成模型供应商、内容安全、数据出境/数据处理、成本和故障降级评审。
7. 完成产品、架构、安全和资金一致性联合评审后再实现 W1/W2 工具。

## 18. 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 模型幻觉金额、商品或状态 | 错误决策或误付款 | 权威工具数据 + 确定性卡片 + 原生确认 |
| 联系人误匹配 | 转错人 | 仅联系人/完整手机号；重名强制选择；脱敏资料复核 |
| 提示注入 | 越权工具调用 | 固定白名单、Schema、策略引擎、最小 scope、工具输出隔离 |
| 重试造成重复交易 | 重复扣款或订单 | 端到端幂等键、状态查询优先、SSE 展示与执行分离 |
| 外卖与支付状态不一致 | 已付款未履约或错误退款 | Saga、Outbox/Inbox、幂等状态机、恢复任务和告警 |
| 敏感数据进入模型 | 隐私和安全事故 | 本地预处理、占位替换、最小聚合、日志字段级脱敏 |
| 新 Commerce 范围扩大 | 交付延期 | 仅沙箱商家、钱包支付、固定模拟履约和全额退款 |
| LLM 供应商锁定 | 成本和迁移风险 | 供应商适配端口、结构化工具契约、模型无关验收集 |

## 19. 版本规划

### P0：沙箱 MVP

- 中文文字对话。
- AI 转账、余额/账单分析。
- AI 原生卡片外卖完整闭环。
- 钱包余额支付、取消和全额退款。
- 显式长期记忆和确定性降级。

### P1：体验增强

- 语音输入和播报。
- 再来一单、常用组合和主动订单提醒。
- 预算提醒、低余额提醒和充值/提现页面引导。
- 更多沙箱支付方式、优惠券组合、发票和配送异常处理。
- 受控 WebView 或标准 API 接入真实外卖项目。

### P2：商用评估

- 真实商家与履约、真实资金和合规运营。
- 细粒度限额授权与可撤销代理权限。
- 更复杂售后和人工客服协同。

自动付款、定时转账和免确认资金动作只有在独立安全、风控、合规和责任边界评审通过后才允许进入后续 PRD，不因本版本预留能力而默认开放。
